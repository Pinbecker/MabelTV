Proposed build, when authorised

Use a Find anything / Find downloads tab beside BBC iPlayer. The phone uses
the existing authenticated portal. The Pi keeps durable requests and progress;
Windows Studio performs source searches, downloads and media preparation.
Studio talks directly to the authenticated local qBittorrent API. A browser
does not open magnet links, and qBittorrent's API is not published on the domain.

Search only when requested. Fetch a bounded candidate set, restrict it to film
and television releases, deduplicate by torrent identity, rank it, then show the
best ten. The API's first ten returned entries are not necessarily the best
ten. Include useful size, seed and release information so a choice is informed.
Search and torrent control do not need OpenAI calls. Reuse the selected title's
existing metadata match throughout the download and Studio handoff.

Resolve magnet metadata before committing to a large download. For a season
pack, inspect the file list and let the owner choose episodes; do not turn a
whole series into unrelated cards or download every included file blindly.
qBittorrent supports stopping at MetadataReceived. Disk admission should allow
for both the selected original and the prepared output. Downloads should use
isolated job directories inside the existing Studio working area, outside
iCloud, with explicit destinations when creating each torrent.

Persist the portal job ID, torrent hashes, selected files and destination.
Scope every qBittorrent action to that job; never stop/remove unrelated torrents
or use a global 'all' action. Reconcile existing hashes after a restart so a
recovered claim does not add the same torrent again. Use existing Studio claims,
heartbeats and durable local transfer journals rather than introducing a
second independent portal job system.

Progress stages should be Getting details, Downloading, Preparing, Sending or
Saving, and Complete. Report size/progress, speed, ETA where available, and
actionable pause/retry states. Retain the existing Studio connection line as
the place for hardware/connection wording. Searches and downloads wait safely
when Studio is unavailable and resume after Windows sign-in through the
existing Studio startup mechanism. Live new search results require that worker
to be connected; cached results must be labelled accordingly.

On completion, first persist a receipt of the completed files and torrent
identity. Use built-in per-torrent limits to stop completed seeding even if
Studio is temporarily unavailable. Verify the stopped state, remove only that
torrent with deleteFiles=false, then hand its retained video files into the
existing Studio file queue. Recover a crash between those steps from the saved
receipt, without downloading again or creating duplicate publications.

Reuse Where should it go? for My TV, a Mabel TV channel, Download, or iCloud,
and retain Keep optimised copy. Keep original downloads through the handoff;
separate retained conversions follow the existing choice. Match films/series,
prepare on Windows and publish through the existing resumable Pi APIs. Subtitle
sidecars or extracted text subtitles can accompany Pi publications; iCloud
saves stay video-only. Existing iCloud layout rules still apply: standalone
films loose, franchises with at least two distinct owned films in folders,
and the owner's numbered MCU, Disney and Julia Donaldson groupings preserved.

Limits and remaining integration checks

BitTorrent exchanges pieces during a download. Stopping completed seeding is
supported; this must not be described as a guarantee of zero upload while
downloading. Source uptime, indexing and available peers determine whether a
particular result can finish. Seed counts are a selection aid, not a guarantee.
Provider changes must cause a useful retry/availability state, not silent
failure. Community search plugins need versioned review when updated.

The completed-file test establishes control, restart behaviour and data
retention. A real peer download through the new portal-to-Studio workflow
remains an implementation acceptance test. That phase also needs interrupted
downloads, worker restarts, multifile season selection, disk-full handling,
malformed results, media validation and a real installed-iOS-PWA review.
Non-media payloads must not be executed. Fail unsupported or encrypted archives
with a useful state rather than passing them blindly to the media pipeline.
